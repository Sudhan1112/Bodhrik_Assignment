# Ledger design notes

## Schema shape

Ledger uses a single users table for admin, provider, and customer, with provider-only usiness_name and io left nullable. That is enough while the provider surface is two fields; splitting into provider_profiles becomes worthwhile when provider data grows (hours, services catalog, media, org membership) or when non-provider rows start carrying unused nulls that complicate indexing and validation. Reviews denormalise provider_id from the booking so public provider review lists never join through ookings — a deliberate read-path optimisation. The cost is keeping that column in sync on write (today the API always copies from the booking at review create). Database constraints enforce one review per booking and rating 1–5; application code still validates completed-only reviews because that rule depends on booking state, not a single-table check. UUID primary keys keep IDs opaque and merge-friendly; Postgres gen_random_uuid() backs inserts while the app also generates UUIDs for portability in tests.

## RBAC evolution

Access is two layers: a route-level 
equire_role gate, then a single ssert_booking_access for row ownership, plus ssert_status_transition for who may fire each status edge. Adding a fourth role (for example staff) means extending the role enum, updating route gates, and teaching the ownership and transition helpers about the new role’s scope — preferably still in those two functions so handlers stay thin. Nested organisations change the model more deeply: providers belong to an org, and an org-admin must manage several providers’ bookings. Row checks would stop comparing user.id == booking.provider_id and instead resolve membership (org_id on the booking or via a memberships table) and grant admin-like bypass within that org. The transition role table would grow the same way — org-admin allowed wherever provider is allowed for members of their org — without scattering comparisons through handlers.

## Production gaps

This slice is not production-safe as shipped. Migrations are Alembic-backed for compose, but CI/tests use SQLite schema create — a dual-path that can drift; production should run only Alembic against Postgres with expand/contract discipline. Secrets (SECRET_KEY, DB passwords) are compose defaults and must move to a secret manager. Open admin registration must be removed. JWT bearer tokens in localStorage are XSS-exposable; prefer httpOnly secure cookies with CSRF protection. There is no token revocation or refresh rotation. Booking overlap is not prevented — concurrent slots for one provider can collide. Rate limiting, structured logging, metrics, and tracing are absent. The summarise worker has no retry budget or dead-letter queue; a poison job can loop or vanish. GET /providers and GET /providers/{id}/reviews are unbounded — a deliberate v1 cut that needs cursor pagination before real traffic. Customer cancel of a confirmed booking is intentionally forbidden (avoids fee/notice logic); the booking detail UI tells customers to contact the provider, who alone can cancel after confirm.
