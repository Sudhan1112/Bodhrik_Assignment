# Ledger — written assessment note

Ledger uses a single `users` table for `admin`, `provider`, and `customer`. Provider-only columns (`business_name`, `bio`, media URLs, city, category, `review_summary`) stay nullable while the provider surface is still modest. That avoids an early `provider_profiles` join on every marketplace read; the tradeoff is sparse nulls for customers and a later migration when hours, galleries, verification, or org membership grow. Services and weekly `availability_rules` are first-class so bookings do not invent free-form duration and price. Bookings store `service_id` plus denormalised `service_name` so history survives rename or deactivation. Reviews are one-per-booking with database rating checks; `provider_id` on reviews is denormalised for fast public listing. Overlap prevention is application-level today; a Postgres exclusion constraint would be the next hardening step.

RBAC is two layers: FastAPI `require_role` dependencies on routes, then centralized row checks and an owned status machine in `rbac.py`. Adding a fourth role means extending the role enum, route gates, `assert_booking_access`, and the transition-role table in those same places — not scattering ad-hoc checks through handlers. Nested organisations would replace `user.id == booking.provider_id` with membership resolution so an org-admin inherits provider powers across members. Services and availability already scope by `provider_id`; org scope would add `org_id` filters the same way. Admin today is a privilege overlay (read any booking, fire legal transitions, trigger summarise) without a dedicated admin UI or router.

For production safety: Alembic expand/contract migrations run against Postgres in Compose and normal deploys, but tests use SQLite `create_all`, so Postgres-only constraints are not fully exercised in pytest. Compose ships default database passwords and a fixed `SECRET_KEY`; production needs secrets from a vault or platform environment, closed admin registration, httpOnly cookies instead of JWT in `localStorage`, token revocation, timezone-aware calendars, payments, real LLM summarisation with job status and a dead-letter queue, rate limits, observability, and broader list pagination. Customer cancel after confirm is intentionally provider-owned in the status machine. Redis is used for two real paths only: a short-TTL booking-list cache and the `jobs:summarise` queue consumed by a worker stub — not as decoration in Compose.
